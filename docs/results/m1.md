# M1 results

Recorded 2026-10-24/25 on the author's machine: Intel Core i7-13700H (20 logical cores), 13.7 GB
RAM, NVIDIA GeForce RTX 4050 Laptop GPU (6 GB, driver 596.36), Windows 11, Python 3.14.5,
PyTorch 2.14.1+cu130, transformers 5.20.2. About ten other builds were running on the machine at
the same time, so absolute timings are pessimistic; the comparisons between policies ran
back-to-back on the same model and workload. CI re-runs the tests on Ubuntu with Python 3.12 and
CPU-only PyTorch.

Model: `openai-community/gpt2` (124M parameters), revision
`607a30d783dfa663caf39e06633721c8d4cfcd7e`, loaded from `model.safetensors`. The downloaded files
were deleted after the runs; every command below downloads the same revision again into
`.tmp/hf` (`HF_HOME`).

## Correctness on real weights (`make verify`)

`lie verify --model openai-community/gpt2 --device cpu` (float32) compares the engine with the
`transformers` implementation of the same checkpoint on four prompts:

    MATCH 'The capital of France is' -> ' the capital of the French Republic, and the capital of ...'
    MATCH 'In a shocking finding, scientists discovered a herd of unicorns' -> ' that were found in a forest ...'
    MATCH 'def fibonacci(n):' -> '\n\nreturn n\n\ndef fibonacci(n):\n\nreturn n ...'
    MATCH 'Continuous batching lets a server' -> ' run a batch of code in parallel. ...'
    max |logit difference| over prompt positions: 6.10e-05
    greedy continuations identical to transformers: 4/4 (32 tokens each)

The four continuations were generated together in one continuous batch.

## Benchmark: naive vs static vs continuous (`make bench-gpu`)

so every policy generates exactly the same tokens), max batch 16, max sequence length 512, GPT-2
in float16 on the RTX 4050. Each policy gets a warm-up pass first. TTFT and latency are measured
from each request's arrival.

## What the numbers say (Analyze)

- **Batching pays because one decode pass costs about the same at batch 1 and batch 12.**
  Naive spends 94.1 s on 2,189 forward passes (43 ms each); continuous spends 8.0 s on 217 passes
  (185 decodes plus 32 prefills, 37 ms each). At this model size the pass is dominated by Python
  and kernel-launch overhead, not by arithmetic, so sharing a pass across 11.7 sequences on average
  gives 11.7x the throughput (272.7 vs 23.3 tokens/s).
- **Continuous beats static by 46% on throughput and 5.6x on median TTFT** for the same work. Static
  keeps its slots until the longest request of the batch finishes (mean batch 8.6 of 16, 250
  passes); continuous refills a slot the step after it frees (mean batch 11.7, 185 passes).
- **Under steady load the difference is latency.** At 4 requests/s continuous serves the first
  token in 84 ms (p50) and 134 ms (p95), because a new request is prefilled at the next step;
  static makes it wait for the running batch to drain (4.0 s p50), and the naive server cannot keep
  up at all (one request at a time, 44 s p50 TTFT as the queue grows).
- **Memory is the price, and it is reserved, not used.** The 16-slot cache holds 288 MiB of KV
  (16 slots x 512 positions x 12 layers, K and V, float16) whatever the request lengths; peak
  allocated memory goes from 272 MiB (naive, one slot) to 550 MiB. The longest request here needs
  256 positions, so at least half of the reserved KV memory is never written: the M2 problem.
- **Gap to a real server:** absolute numbers are low for a 124M model on a GPU (no CUDA graphs, no
  fused kernels, prompt prefill one at a time, a loaded machine). The vLLM comparison on the same
  model and workload is M3; nothing here is compared with vLLM yet.

## Improve

- **Device sync per layer.** The first GPU attempt (64 requests) did not finish within 400 s. The
  decode pass read the longest prefix length from a GPU tensor (`positions.max().item()`) in every
  layer, which forces a CPU-GPU sync 12 times per step. The engine now passes the span it already
  knows from its own bookkeeping, so a decode step has no extra syncs; the numbers above were
  measured after this change, and the workload was reduced to 32 requests to keep the GPU run short.
- **Vulnerable dependencies.** `pip-audit` reported setuptools 81.0.0 (PYSEC-2026-3447,
  GHSA-xmj3-9gf7-h52w) pulled in by PyTorch 2.11 (which pins setuptools<82), and filelock 3.32.3
  (three CVEs fixed in 4.2.1). PyTorch was moved to 2.14.1, setuptools to 84.2.1 and filelock to
  4.2.1; the audit is now clean.

## Quality control (DMAIC)

| Phase | This repository |
|---|---|
| Define | Serving an LLM one request at a time wastes most of each forward pass, and static batches hold slots until their longest request ends; this affects engineers who run or evaluate LLM serving stacks. M1 counts when a naive server, static batching and continuous batching run on the same engine, the engine matches `transformers` on GPT-2, batching never changes tokens, and continuous batching reaches at least 3x the naive throughput ([RFC 0001](../rfc/0001-design.md)). |
| Measure | `make test`, `make verify` and `make bench-gpu` on GPT-2 (124M, revision 607a30d), RTX 4050 Laptop GPU, plus ruff, `mypy --strict` and `pip-audit`. 36 tests passed; max logit difference 6.1e-05 and 4/4 identical greedy continuations; 23.3 / 186.4 / 272.7 tokens/s for naive / static / continuous with 32 queued requests; TTFT p50 84 ms for continuous at 4 requests/s. |
| Analyze | A decode pass costs about the same at batch 1 and batch 12 at this model size, so throughput scales with the mean batch; static batching loses 46% throughput and 5.6x median TTFT to continuous because finished slots stay idle. One defect was found (a GPU sync per layer that made the first run time out) and two vulnerable transitive dependencies. |
| Improve | The decode span comes from the scheduler's bookkeeping instead of a device read; PyTorch 2.14.1, setuptools 84.2.1 and filelock 4.2.1 clear the audit. |
| Control | The `ci` workflow runs ruff, ruff format, `mypy --strict`, the 36 tests and `pip-audit` (with PyTorch audited by its PyPI version) on every push, plus a tiny-model benchmark with a `::notice` result, and a `gpt2` job that runs `lie verify` against `transformers` (CI job written; first CI run pending). In code: batched output must equal naive output (tested on random arrival schedules), requests are bounded (prompt length, `max_tokens`, queue size), checkpoints need a full commit hash and load strictly from safetensors. |
